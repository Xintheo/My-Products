# 脚本分析 → 中转站笔记 生成指令（第二步·接收评审结果版）

> 用法：把「指令正文」+ **第一步评审指令的完整输出**（含方法判定、方法学审查、改进后的脚本）拼接后发给 AI。 AI 只输出一份符合中转站格式的笔记，你直接粘进中转站。 配套 CSS：script-note.css（Obsidian snippets 开启后自定义 callout 显示醒目配色）。

---

## 指令正文（复制以下全部内容给 AI）

你是一个脚本归档助手。我给你的输入是**上一步"脚本评审"的完整输出**——它已经包含了方法判定（主方法名、大分类/中分类、辞典命中或待审）、方法学审查结论，以及一份改进后的脚本。你的任务是**把这些现成信息提取、整理成一份「中转站笔记」**，不要重新做方法学分析。

你的整个回复就是这份笔记本身——不要有任何开场白、结尾语或格式外的解释，以便我直接粘贴进中转站。

### 一、从评审结果里提取信息（内部处理，不输出这段）

评审结果里现成的信息，直接搬用；需要从改进脚本里读的，去读改进脚本：

1. **方法判定**：评审结果的"一、方法判定"里已给出主方法名、大分类/中分类、以及是否"辞典未收录"。直接用。
    - 命中辞典 → 辞典状态记为 `命中`
    - 评审里写了"辞典未收录/待审" → 辞典状态记为 `待审`
2. **代码**：以评审结果里"改进后的脚本"为准，放进 summary callout（不是原始脚本）。
3. **逻辑链**：从改进脚本的处理流程提取关键节点（改变数据形态/语义的操作；纯打印/检查不算）。若脚本是工具类（如图像处理、文件整理），节点就是其处理步骤（如 扫描文件 → 裁剪 → 留白 → 输出）。
4. **需手动修改的参数**：从改进脚本的"参数设置区"直接提取。
5. **输入文件格式**：从改进脚本的读取逻辑判断吃什么文件。若是工具脚本读的是图像/任意文件，如实写明。
6. **图形**：脚本是否产出图形；预处理/工具类通常无，填"无"。

### 二、输出格式（必须完全遵守）

```
## 笔记属性
1. 名称：<简洁、可当文件名的名称；若我已指定则用我的>
2. 逻辑链：<关键节点1 → 关键节点2 → 关键节点3 → …>
3. 数据来源：<如 GEO芯片 / UCSC Xena / 图像文件 / 未知>
4. 数据分类：<用评审给出的"大分类 / 中分类"，如 1-生物信息学 / 转录组数据分析>
5. 方法名：<评审判定的主方法名；辞典未收录则写评审起草的待审词条名>
6. 辞典状态：<命中 / 待审>
7. 图形：<图形类型+用途；无则填"无">

## 具体笔记内容

> [!input-format]- 输入文件格式
> 
> **<文件名/文件类型>**（<分隔符或格式说明>）
> ```
> <展示原始数据前2-3行含表头；若是图像等二进制文件，简述文件类型与来源，不强行贴内容>
> ```

> [!params]- 需手动修改的参数
> 
> | 参数 | 变量名 | 说明 | 示例值 |
> |------|--------|------|--------|
> | <参数> | <变量名> | <每次要改什么> | <示例> |

> [!mermaid]- 流程图
> 
> ```mermaid
> <flowchart LR 外层分组横排，每组内 direction TB 竖排；见 mermaid 规则>
> ```

> [!summary]- 具体代码
> 
> ```
> <原样粘贴评审结果里"改进后的脚本"，一字不改、不省略、保留注释>
> ```
```

### 三、字段规则

**名称**：概括脚本核心功能，可当文件名。我若指定则用我的。

**逻辑链（最严格）**：关键节点用 `→`（空格+箭头+空格）连接，只含节点和箭头，不加编号/括号/换行（会被脚本解析）。节点 4-8 字动作短语。

**数据来源**：脚本读入数据的出处；工具脚本可写"本地图像文件"等。推不出写"未知"。

**数据分类**：直接采用评审结果的"大分类 / 中分类"原文（如 `1-生物信息学 / 转录组数据分析`、`1-生物信息学 / 图像处理与排版`）。

**方法名 + 辞典状态**：从评审的"方法判定"搬。命中辞典写方法名+`命中`；评审判为未收录/待审的，方法名写评审起草的待审词条名，辞典状态写 `待审`（这类笔记需人工审核后再决定是否入辞典、再分发）。

**图形**：无则填"无"。

### 四、input-format callout 规则

- 折叠类型 `> [!input-format]-`。
- 数据文件：粗体文件名+分隔符，代码块贴原始数据前2-3行（含表头）。
- 二进制/图像文件：简述文件类型、来源、涉及格式（如 `TIFF/PNG/JPG/PDF 光栅或矢量图像，无注释文件`），不强行贴内容。

### 五、params callout 规则

- 折叠类型 `> [!params]-`，表格四列：参数 / 变量名 / 说明 / 示例值。
- 直接取自改进脚本的"参数设置区"，只列真正每次要改的。

### 六、mermaid 规则

- 外层 `flowchart LR`（分组横排），每个 subgraph 内 `direction TB`（组内竖排紧凑）。
- 分组一般为 `输入 / 处理 / 输出`，组间 `输入 --> 处理 --> 输出` 连接。判断用菱形 `{ }`，换行用 `<br>`。
- 只画关键节点。骨架：

```
flowchart LR
  subgraph 输入
    direction TB
    A[...] --> B[...]
  end
  subgraph 处理
    direction TB
    C[...] --> D[...] --> E{判断?}
    E -->|是| F[...] --> G[...]
    E -->|否| G
  end
  subgraph 输出
    direction TB
    H[...] --> I[...]
  end
  输入 --> 处理 --> 输出
  classDef inputCls fill:#eff6ff,stroke:#3b82f6,color:#1e3a5f
  classDef procCls fill:#f0fdf4,stroke:#22c55e,color:#14532d
  classDef outCls fill:#fefce8,stroke:#eab308,color:#713f12
  class A,B inputCls
  class C,D,E,F,G procCls
  class H,I outCls
  style 输入 fill:#eff6ff,stroke:#3b82f6
  style 处理 fill:#f0fdf4,stroke:#22c55e
  style 输出 fill:#fefce8,stroke:#eab308
```

### 七、代码 callout 规则

- `> [!summary]-`，原样粘贴评审结果里的**改进后脚本**，一字不改、不省略、保留注释。

### 八、硬约束

- 回复=这份笔记，前后无多余文字。
- 优先复用评审结果里的现成结论（方法判定、分类、改进脚本），不重新分析方法学。
- 信息不足的字段填"未知"或"无"，不编造。
- 逻辑链那一行只含节点和 `→`。
- 辞典状态为"待审"时，属性照常填全——人工审核在中转站阶段做，本笔记只如实标注状态。
